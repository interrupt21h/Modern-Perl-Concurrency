\chapter{Building concurrent Catalyst applications with Memcached}
\label{ch:memcached-capstone}
\chapterbrief{Separate disposable cache coordination from durable authorization and transactional invariants.}
This companion to the Redis Catalyst laboratory uses four Starman workers, Memcached and InnoDB. Memcached supplies bounded compare-and-swap (CAS) retries and best-effort rate counters. The database owns bearer-token authorization and idempotent order records. No cache entry is authoritative for authentication or financial effects.

\section{Authentication and the API contract}
An application programming interface (API) defines how clients interact with the service. The application serves its OpenAPI 3.1 contract at \code{/openapi.json}. Opaque 256-bit bearer credentials are provisioned by the laboratory driver; only Secure Hash Algorithm 256-bit (SHA-256) digests, scopes and expiration times are stored in the database. Read credentials cannot mutate counters or orders. Revocation removes the credential from the authoritative store. A request already authorized before revocation may complete. Use Transport Layer Security (TLS) outside the loopback laboratory and never log bearer credentials. This example does not implement an OAuth authorization server or browser cookie sessions.

\section{CAS and durable idempotency}
The counter reads a CAS token and attempts a conditional replacement. Contention triggers a bounded retry with jitter; an absent key is initialized with add-if-absent. Eviction can reset the counter, so it is not a durable total. The rate counter is likewise advisory and can reset on eviction. An unavailable cache returns an error rather than silently bypassing the rate check.

The order endpoint uses a unique database key scoped to the authenticated principal. Concurrent identical submissions return the same stored amount; reuse with a different amount returns a conflict. The database row is the simulated effect, not a real payment. External effects require a transactional outbox and downstream idempotency.


\section{Responsibility map: who owns what?}
Hypertext Transfer Protocol (HTTP) carries requests and responses; Structured Query Language (SQL) carries database operations. JavaScript Object Notation (JSON) encodes API responses. A worker is a process, not a shared object. Each request may reach a different worker. Perl variables in one worker cannot coordinate another worker. Shared state therefore lives behind a service boundary. The following map distinguishes the owner of a decision from the component that merely executes it.

\noindent\textbf{Alternative paths.} Missing or expired credentials return 401; insufficient scope returns 403; malformed input returns 400. Cache failure returns 503, and a rate limit breach returns 429. A different amount under the same order key returns 409. None of these paths requires a new durable order.

A rate window uses a key containing the principal and minute number. Concurrent add operations initialize at most one live key; incr updates that key atomically. Expiration removes obsolete windows. Eviction can nevertheless reset a live window, so a strict abuse quota needs a stronger authority. Likewise, the advisory lease in example 14 can coalesce cache refreshes but must not protect a payment: eviction or expiry can admit a second owner. A CAS tombstone avoids deleting a successor's lease, but cannot restore mutual exclusion after the original lease has expired.

\noindent\textbf{Reader exercise.} Trace two requests with the same order key but different amounts. Identify the unique index as the arbitration point, the stored amount as the decision input, and HTTP 409 as the losing request's outcome. Then repeat with an evicted counter key. Explain why only the latter operation may restart its count.

\section{Executable laboratory}
Run example 40 against disposable MySQL and Memcached services. The driver starts four workers, checks the served API contract, exercises missing credentials and insufficient scope, submits eight concurrent increments and eight duplicate orders, deletes cache entries and verifies the durable order remains unique. It then revokes the token and checks that subsequent authentication fails. A successful run prints an explicit final success line; consult the release verification record for observed results.
